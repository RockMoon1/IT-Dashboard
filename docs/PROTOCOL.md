# ARH agent link protocol (version 2)

The host (ARH IT Dashboard on the technician's Windows PC) never connects _into_ a target. The
agent on the target makes one outbound TLS connection to the host over the USB network link and
keeps it open. Everything below is what travels on that connection and how trust is established.

## Ports and discovery

| Direction    | Transport     | Port  | Purpose                                             |
| ------------ | ------------- | ----- | --------------------------------------------------- |
| host → link  | UDP broadcast | 47911 | beacon: "a dashboard is on this link, connect here" |
| agent → host | TCP + TLS 1.3 | 47912 | the session                                         |

Beacon payload (JSON, one datagram every 2 s on every link adapter):

```json
{ "arh": 1, "port": 47912, "fp": "3f9a1c2b7e4d6a10", "hostId": "d1f4…" }
```

`fp` is the first 16 hex characters of the SHA-256 fingerprint of the host's TLS certificate.
The agent only _uses_ the beacon to learn an address; it never trusts a beacon.

Why host-broadcast and not agent-broadcast: the agent is already running elevated at install
time and can open its own inbound UDP firewall rule; the dashboard is not elevated, and sending
a broadcast needs no rule. The host still needs one inbound TCP rule for 47912 (a one-time
UAC prompt from the dashboard).

## Identities

- **Host identity**: a self-signed ECDSA P-256 certificate generated once on first launch by
  the bundled agent binary (`arh-agent host-cert`). The private key goes into Windows Credential
  Manager (`ARH IT Dashboard/host-tls-key`); the certificate (public) sits in the app data folder.
- **Device identity**: a self-signed ECDSA P-256 certificate generated by the agent at install
  time. The private key goes into the target's OS keystore (Windows: DPAPI machine scope;
  macOS: System keychain; Linux: root-only file). The host pins the certificate's SHA-256
  fingerprint; that fingerprint _is_ the device id.
- TLS is mutual: the host presents its certificate, the agent presents its device certificate.
  Neither side uses the system CA store. Verification is by pinned fingerprint on both sides.

## Enrollment (first contact)

1. The dashboard shows a one-time token, valid 10 minutes, single use:

   `ARH-<fp8>-<secret16>` e.g. `ARH-3F9A1C2B-7Q3KM8ZTXW2P4H6N`

   `fp8` = first 8 hex chars of the host certificate fingerprint (sanity check only);
   `secret16` = 80 random bits in Crockford base32 (the shared secret).

2. The technician runs the install step on the target (admin / sudo):
   `arh-agent install --token ARH-…`. The agent generates its device key and certificate,
   stores them, installs itself as a system service and starts.
3. The agent hears a beacon, opens TLS to the host, verifies the host certificate fingerprint
   starts with `fp8`, and sends:

   ```json
   {
     "type": "enroll",
     "token": "ARH-…",
     "nonce": "<32 random bytes, base64>",
     "hostname": "LAPTOP-01",
     "serial": "ABC123",
     "os": "windows",
     "agentVersion": "0.1.0"
   }
   ```

4. The host checks the token (unused, unexpired) and proves it knows the secret:

   ```json
   {
     "type": "enroll-proof",
     "proof": "<hex HMAC-SHA256(secret, nonce || hostFingerprint)>",
     "hostFingerprint": "<full sha256 hex>"
   }
   ```

5. The agent recomputes the HMAC. On match it pins `hostFingerprint` permanently and replies
   `{ "type": "enroll-confirm" }`. The host records the device (fingerprint of the client
   certificate from the TLS handshake, serial, hostname, OS), marks the token used, and replies
   `{ "type": "enrolled", "deviceId": "<fingerprint>", "displayName": "LAPTOP-01" }`.
6. Any failure ends the connection; the token stays usable until it expires unless step 5
   completed.

A man-in-the-middle on the link cannot pass step 4 without the secret, and cannot pass the TLS
client-certificate binding without the device key.

## Session (every later connection)

```
agent → host  { "type": "hello", "hostname", "serial", "os", "agentVersion", "profiles": [{ "name", "version" }],
                "protocol": 2, "link": "cable" | "lan", "bootTime", "actions": [{ "name", "version", "sha256" }],
                "policy": { "write", "execute", "custom", "lan", "interrupts", "deny": [], "error"? },
                "running"?: "<runId>", "pendingRestartUntil"?: "<ISO-8601>" }
host → agent  { "type": "welcome", "deviceId", "hostTime": "<ISO-8601>" }   (or { "type": "reject", "reason" })
agent → host  { "type": "result", "runId", "result": { … } }   once per result still in the outbox
either side   { "type": "ping" } / { "type": "pong" }   every 20 s; 60 s silence closes the socket
agent → host  { "type": "policy", "policy": { … } }   when policy.json changed on the device
agent → host  { "type": "state", "pendingRestartUntil"?: "<ISO-8601>" }   when a restart is
              scheduled or cancelled, or its wait ends (no field: no restart pending)
```

Protocol-1 agents send none of the protocol-2 fields; the dashboard then treats the device as
read only. `link` is `cable` only when the TCP peer is link-local and the agent's end of the
connection is not on the interface that carries its default route.

The host looks the client certificate fingerprint up in its device registry. Unknown
fingerprints are rejected (`reject`), and the dashboard shows the device as "needs enrollment".

## Running a scan profile

The host never sends commands. It names a profile the agent already carries:

```
host → agent  { "type": "run", "runId": "r_…", "profile": "windows-system-diagnostics", "version": 1 }
agent → host  { "type": "run-start", "runId", "profile", "version", "checks": 7 }
agent → host  { "type": "check-start", "runId", "checkId", "title", "category" }
agent → host  { "type": "check-output", "runId", "checkId", "stream": "stdout" | "stderr", "data": "…" }   (chunks)
agent → host  { "type": "check-end", "runId", "checkId", "exitCode": 0, "durationMs": 812, "timedOut": false, "truncated": false }
agent → host  { "type": "run-end", "runId", "ok": true, "durationMs": 9120, "error": null }
host → agent  { "type": "abort", "runId" }
```

Rules enforced by the agent, not the host:

- The profile name and version must match an embedded profile byte-for-byte (the agent carries
  `profiles/*.json` compiled in). Otherwise `run-end` with `ok:false, error:"unknown profile"`.
- Every check must have `"access": "read"`. Changes are not scan checks: they are named actions
  (next section), with their own rules.
- Output per check is capped at 1 MiB (then `truncated: true`); per-check timeout from the
  profile (default 90 s); the whole run is aborted on `abort` or if the socket closes.
- Output is read as fast as the check writes it, whatever the speed of the link: a slow link
  delays `check-end` but drops nothing under the cap.
- A `check-output` chunk never ends inside a UTF-8 character, whatever its length: a character
  that reaches the agent in two reads is sent whole in the later chunk. Bytes that are not UTF-8
  are sent as they come, and so arrive as U+FFFD.
- A check (or action script, or custom command) whose shell exits while a process it started in
  the background still holds its output (`nohup … &` without redirecting it) keeps the shell's
  exit status, whatever it is. Its output is read for 2 s more and then cut, with
  `truncated: true`: what that process writes later is not collected. On Linux and macOS that
  process is left running (a timeout or abort ends the whole process group, but only while the
  shell runs), though a write to the cut output then ends it unless it ignores SIGPIPE; on Linux
  systemd also ends it when the agent's service stops or restarts. On Windows the Job Object ends
  it with the check.

## Actions and custom commands (protocol 2)

Design and rationale: [PHASE3-DESIGN.md](PHASE3-DESIGN.md). The host still never sends a
script for a named action: it names one the agent carries, with the version and the SHA-256 of
its file.

```
host → agent  { "type": "action", "runId": "a_…", "action": "windows-firewall-on", "version": 1, "sha256": "…",
                "params": { "name": "value" }, "mode": "preview" | "apply", "technician", "reason" }
host → agent  { "type": "exec", "runId": "x_…", "shell": "powershell" | "sh", "script": "…", "timeoutSeconds": 300,
                "technician", "reason" }
agent → host  { "type": "run-start", "runId", "action", "version", "sha256", "mode", "params", "timeoutSeconds", "checks", "title", "link" }
agent → host  check-start / check-output / check-end with checkId "measure", "apply", "measure-after" (or "exec")
agent → host  { "type": "run-end", "runId", "ok", "durationMs", "result": { … } }
              or, when refused, { "type": "run-end", "runId", "ok": false, "errorCode", "error" }
host → agent  { "type": "ack", "runId" }        the result is recorded; drop it from the outbox
host → agent  { "type": "abort", "runId" }      answered by { "type": "abort-refused", "runId", "errorCode", "error" } when unsafe
```

`result` is the agent's `actions.Result`: the measured `before` and `after` (items, info, plan,
blockers, warnings, restore values), what `apply` reported, `applied`, `skipped`, `aborted`, and
the device's own times. `tests/fixtures/protocol/actions.ndjson` is decoded by both the Go and the
TypeScript tests.

Rules enforced by the agent:

- `mode` is required; anything but `preview` or `apply` is refused (`bad-mode`). A preview runs
  only the action's measure script.
- Name, version and SHA-256 must match an embedded action (`unknown-action`, `version-mismatch`);
  parameters must be declared and pass the action's own checks (`bad-param`).
- `apply` and `exec` need the device's `policy.json` to allow them (`policy-denied`; missing or
  invalid file means read only) and a cable session (`lan-session`), unless the policy allows LAN.
  `exec` needs custom, write and execute all allowed.
- A run id is used once (`duplicate-run`; the stored result is sent again). One run at a time
  (`busy`), except actions marked concurrent. After a restart is scheduled, other changes wait
  (`restart-pending`).
- Once apply has started, the run is no longer tied to the session: it finishes if the cable is
  pulled, and its result waits in the outbox until acknowledged. Abort stops a measure, an
  abortable apply or a custom command; otherwise `not-abortable`. A stop that arrives before
  apply starts is honoured: the change is not started. A custom command whose process never
  started (aborted first, sent while the agent is stopping, or the shell could not start) comes
  back with `applied: false`, no `appliedAt`, and `skipped` saying why.
- A run the agent itself was stopped in the middle of (shutdown, restart, the agent stopped or
  killed) is sent on the next connection as a result with `aborted: true`, the error "the agent
  stopped before this run finished …", what was measured before, and `applied` saying whether the
  change had started. When the agent is stopped on Linux or macOS, a running change or custom
  command gets 15 seconds to finish and report normally first; a custom command still running
  then is ended and reported as aborted. On Windows the Job Object ends what the agent started
  when the agent ends.
- Every action and custom command is recorded on the device (`actions.log`, intent before the
  process starts and outcome after, never output) and in the OS log.

## Message framing

Newline-delimited JSON (one object per line, UTF-8, `\n` terminated, maximum 256 KiB per line).
Unknown message types are ignored; malformed lines close the connection.

## Scan profile file format

```json
{
  "schema": "arh-scan-profile/1",
  "name": "windows-system-diagnostics",
  "version": 1,
  "os": "windows",
  "purpose": "system-diagnostics",
  "title": "System Diagnostics",
  "description": "OS, hardware, storage, drivers and firmware",
  "checks": [
    {
      "id": "os-overview",
      "title": "OS build, uptime, hardware",
      "category": "System",
      "shell": "powershell",
      "command": ["$os = Get-CimInstance Win32_OperatingSystem", "…"],
      "format": "json",
      "timeoutSeconds": 60,
      "optional": false,
      "access": "read"
    }
  ]
}
```

- `command` is an array of lines joined with `\n`; it is the exact script that runs. No
  templating, no parameters from the host.
- `shell` is `powershell` (Windows: `powershell.exe -NoProfile -NonInteractive -ExecutionPolicy
Bypass -EncodedCommand …`) or `sh` (macOS/Linux: the script on stdin of `/bin/sh -s`).
- `format: "json"` means the host parses the last JSON document on stdout; `"text"` is kept raw.
- `optional: true` means a failure does not fail the run.
- There is one copy: `profiles/*.json`. The Go build embeds it (`profiles/embed.go`) and the
  Electron package ships it as `resources/profiles`, so host and agent cannot drift apart.

## What the agent runs as

Windows: a scheduled task at system start under `SYSTEM`, registered with no execution time
limit and restart-on-failure (no service control dispatcher needed, so the agent has no
third-party dependencies). macOS: a LaunchDaemon (root). Linux: a systemd
unit (root). Running as root/SYSTEM is what lets read-only checks see every user profile, the
Security event log and SMART data; the allowlist above is what keeps that power bounded. Named
actions run in the same context, with a cleared environment, the system PATH and a fixed
working folder; on Windows every run is in a Job Object so a timeout ends the whole process tree.
`arh-agent policy` on the device says what the dashboard may do there.

The systemd unit sends SIGTERM to the agent alone (`KillMode=mixed`), and it and the
LaunchDaemon wait 30 s before SIGKILL, longer than the agent's drain. One agent process uses a
data folder at a time: it holds a lock on `agent.lock` there while it runs (the operating system
releases it when the process ends), so an `arh-agent run` started by hand while the service runs
exits with an error and leaves the service's runs and `actions.log` alone. `status` and `policy`
do not take it.
