# ARH agent link protocol (version 1)

The host (ARH IT Dashboard on the technician's Windows PC) never connects _into_ a target. The
agent on the target makes one outbound TLS connection to the host over the USB network link and
keeps it open. Everything below is what travels on that connection and how trust is established.

## Ports and discovery

| Direction    | Transport     | Port  | Purpose                                             |
| ------------ | ------------- | ----- | --------------------------------------------------- |
| host → link  | UDP broadcast | 47911 | beacon: "a dashboard is on this link, connect here" |
| agent → host | TCP + TLS 1.3 | 47912 | the session                                         |

Beacon payload (JSON, one datagram every 2 s on every link adapter):

```json
{ "arh": 1, "port": 47912, "fp": "3f9a1c2b7e4d6a10", "hostId": "d1f4…" }
```

`fp` is the first 16 hex characters of the SHA-256 fingerprint of the host's TLS certificate.
The agent only _uses_ the beacon to learn an address; it never trusts a beacon.

Why host-broadcast and not agent-broadcast: the agent is already running elevated at install
time and can open its own inbound UDP firewall rule; the dashboard is not elevated, and sending
a broadcast needs no rule. The host still needs one inbound TCP rule for 47912 (a one-time
UAC prompt from the dashboard).

## Identities

- **Host identity**: a self-signed ECDSA P-256 certificate generated once on first launch by
  the bundled agent binary (`arh-agent host-cert`). The private key goes into Windows Credential
  Manager (`ARH IT Dashboard/host-tls-key`); the certificate (public) sits in the app data folder.
- **Device identity**: a self-signed ECDSA P-256 certificate generated by the agent at install
  time. The private key goes into the target's OS keystore (Windows: DPAPI machine scope;
  macOS: System keychain; Linux: root-only file). The host pins the certificate's SHA-256
  fingerprint; that fingerprint _is_ the device id.
- TLS is mutual: the host presents its certificate, the agent presents its device certificate.
  Neither side uses the system CA store. Verification is by pinned fingerprint on both sides.

## Enrollment (first contact)

1. The dashboard shows a one-time token, valid 10 minutes, single use:

   `ARH-<fp8>-<secret16>` e.g. `ARH-3F9A1C2B-7Q3KM8ZTXW2P4H6N`

   `fp8` = first 8 hex chars of the host certificate fingerprint (sanity check only);
   `secret16` = 80 random bits in Crockford base32 (the shared secret).

2. The technician runs the install step on the target (admin / sudo):
   `arh-agent install --token ARH-…`. The agent generates its device key and certificate,
   stores them, installs itself as a system service and starts.
3. The agent hears a beacon, opens TLS to the host, verifies the host certificate fingerprint
   starts with `fp8`, and sends:

   ```json
   {
     "type": "enroll",
     "token": "ARH-…",
     "nonce": "<32 random bytes, base64>",
     "hostname": "LAPTOP-01",
     "serial": "ABC123",
     "os": "windows",
     "agentVersion": "0.1.0"
   }
   ```

4. The host checks the token (unused, unexpired) and proves it knows the secret:

   ```json
   {
     "type": "enroll-proof",
     "proof": "<hex HMAC-SHA256(secret, nonce || hostFingerprint)>",
     "hostFingerprint": "<full sha256 hex>"
   }
   ```

5. The agent recomputes the HMAC. On match it pins `hostFingerprint` permanently and replies
   `{ "type": "enroll-confirm" }`. The host records the device (fingerprint of the client
   certificate from the TLS handshake, serial, hostname, OS), marks the token used, and replies
   `{ "type": "enrolled", "deviceId": "<fingerprint>", "displayName": "LAPTOP-01" }`.
6. Any failure ends the connection; the token stays usable until it expires unless step 5
   completed.

A man-in-the-middle on the link cannot pass step 4 without the secret, and cannot pass the TLS
client-certificate binding without the device key.

## Session (every later connection)

```
agent → host  { "type": "hello", "hostname", "serial", "os", "agentVersion", "profiles": [{ "name", "version" }] }
host → agent  { "type": "welcome", "deviceId", "hostTime": "<ISO-8601>" }   (or { "type": "reject", "reason" })
either side   { "type": "ping" } / { "type": "pong" }   every 20 s; 60 s silence closes the socket
```

The host looks the client certificate fingerprint up in its device registry. Unknown
fingerprints are rejected (`reject`), and the dashboard shows the device as "needs enrollment".

## Running a scan profile

The host never sends commands. It names a profile the agent already carries:

```
host → agent  { "type": "run", "runId": "r_…", "profile": "windows-system-diagnostics", "version": 1 }
agent → host  { "type": "run-start", "runId", "profile", "version", "checks": 7 }
agent → host  { "type": "check-start", "runId", "checkId", "title", "category" }
agent → host  { "type": "check-output", "runId", "checkId", "stream": "stdout" | "stderr", "data": "…" }   (chunks)
agent → host  { "type": "check-end", "runId", "checkId", "exitCode": 0, "durationMs": 812, "timedOut": false, "truncated": false }
agent → host  { "type": "run-end", "runId", "ok": true, "durationMs": 9120, "error": null }
host → agent  { "type": "abort", "runId" }
```

Rules enforced by the agent, not the host:

- The profile name and version must match an embedded profile byte-for-byte (the agent carries
  `profiles/*.json` compiled in). Otherwise `run-end` with `ok:false, error:"unknown profile"`.
- Every check must have `"access": "read"`. Version 1 agents refuse anything else, so a future
  write/execute action needs a new agent build _and_ a per-action approval message that does not
  exist yet.
- Output per check is capped at 1 MiB (then `truncated: true`); per-check timeout from the
  profile (default 90 s); the whole run is aborted on `abort` or if the socket closes.

## Message framing

Newline-delimited JSON (one object per line, UTF-8, `\n` terminated, maximum 256 KiB per line).
Unknown message types are ignored; malformed lines close the connection.

## Scan profile file format

```json
{
  "schema": "arh-scan-profile/1",
  "name": "windows-system-diagnostics",
  "version": 1,
  "os": "windows",
  "purpose": "system-diagnostics",
  "title": "System Diagnostics",
  "description": "OS, hardware, storage, drivers and firmware",
  "checks": [
    {
      "id": "os-overview",
      "title": "OS build, uptime, hardware",
      "category": "System",
      "shell": "powershell",
      "command": ["$os = Get-CimInstance Win32_OperatingSystem", "…"],
      "format": "json",
      "timeoutSeconds": 60,
      "optional": false,
      "access": "read"
    }
  ]
}
```

- `command` is an array of lines joined with `\n`; it is the exact script that runs. No
  templating, no parameters from the host.
- `shell` is `powershell` (Windows: `powershell.exe -NoProfile -NonInteractive -ExecutionPolicy
Bypass -EncodedCommand …`) or `sh` (macOS/Linux: the script on stdin of `/bin/sh -s`).
- `format: "json"` means the host parses the last JSON document on stdout; `"text"` is kept raw.
- `optional: true` means a failure does not fail the run.
- There is one copy: `profiles/*.json`. The Go build embeds it (`profiles/embed.go`) and the
  Electron package ships it as `resources/profiles`, so host and agent cannot drift apart.

## What the agent runs as

Windows: a scheduled task at system start under `SYSTEM`, registered with no execution time
limit and restart-on-failure (no service control dispatcher needed, so the agent has no
third-party dependencies). macOS: a LaunchDaemon (root). Linux: a systemd
unit (root). Running as root/SYSTEM is what lets read-only checks see every user profile, the
Security event log and SMART data; the allowlist above is what keeps that power bounded.
